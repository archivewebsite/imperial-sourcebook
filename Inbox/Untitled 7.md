This recipe is basically **turning a messy life/work problem into a pathfinding problem**. Very annoying that it works, but it does.

The diagram is saying: don’t treat a hard problem like one giant blob called “solve it.” Treat it like a graph.

A **node** is a state of reality.

An **edge** is an action that moves you from one state to another.

The **start node** is where you are now.

The **end node** is the exact outcome you want.

The **intermediate nodes** are the milestones you probably need to pass through.

The red arrows are the “candidate path” through the mess.

The dark arrows are all the other possible actions, detours, dependencies, and chaos humans insist on manufacturing.

The recipe is:

First, define the goal state clearly. Not “get fit,” but “I can run 5 km in under 30 minutes without stopping.” Not “launch a startup,” but “I have 10 paying customers using the product weekly.” A vague goal creates a foggy end node, and then the whole graph becomes soup.

Second, define the current state honestly. This is where people usually lie to themselves for sport. Current state means: what resources do I have, what do I know, what is broken, what constraints exist, what is actually true today?

Third, sketch the rough path. You ask: “What states probably need to be true before the final state can be true?” These become intermediate nodes.

Example:

Goal: “Have 10 paying customers.”

Current state: “I have an idea, no product, no users.”

Possible nodes:

“Problem validated with 20 target users.”

“Basic landing page exists.”

“Prototype solves one painful use case.”

“5 users tried it.”

“First user paid.”

“Sales message works.”

“10 users paid.”

Now the monster has bones.

Fourth, keep splitting big jumps until every step is obvious. This is the real trick.

A bad edge is:

“Build the product.”

That’s not an edge. That’s a swamp with branding.

A better split is:

“Write down the one core workflow.”

“Make a clickable mockup.”

“Show mockup to 5 users.”

“Build only the first screen.”

“Test whether one user can complete the workflow.”

Each hop should be small enough that you can say: “I know what to do next, I know how to check whether it worked, and I don’t need divine intervention.”

Fifth, tackle the first node. Not the whole graph. Just the first move.

That’s why this works: it converts anxiety into navigation. Instead of staring at a complicated thing and waiting for your brain to perform a miracle, you create a sequence of states and reduce uncertainty one edge at a time.

A useful way to apply it is:

“Where do I want to end up?”

“Where am I now?”

“What must be true immediately before the goal?”

“What must be true before that?”

“What is the smallest believable next state?”

“What action moves me there?”

“How will I know I arrived?”

The hidden wisdom is that you don’t need the perfect full path. You need a **credible next hop**. After each hop, your map improves. You learn things. Some arrows disappear, new ones appear, and the path changes. Welcome to reality, the worst project manager.

The phrase “every time I simplified a complex problem to this bad boy over there I won” means: when he turned the problem into a graph of states and transitions, he stopped being overwhelmed and started making controlled progress.

The whole method can be summarized like this:

**Make the goal concrete. Make the present honest. Make the path visible. Make each jump small. Do the first jump. Repeat.**
